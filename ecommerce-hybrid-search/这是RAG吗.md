# 这个项目属于 RAG 吗？

> 读完 [ARCHITECTURE.md](ARCHITECTURE.md) 之后最常见的一个问题。

严格说：**不是 RAG，它是 RAG 的 R。**

---

## 差在哪

RAG = **R**etrieval-**A**ugmented **G**eneration。三个字母缺一不可，
关键在最后那个 G：**把检索到的内容塞进 LLM 上下文，让它生成一段答案**。

这个项目的输出是**一个排好序的商品列表**，直接渲染成搜索结果页给人看。
没有任何一步把召回的商品喂给 LLM 去生成文字。
所以它是检索系统（IR），不是 RAG。

---

## 但这里明明用了三次 LLM

对，而且这正是容易混淆的地方——**用了 LLM ≠ 是 RAG**。
看这三处各自在干什么：

| 位置 | LLM 的角色 | 是 G 吗 |
|---|---|---|
| L0 属性抽取 | 信息抽取器（文案 → 结构化字段） | ❌ 离线批处理，输入是商品文案，不是检索结果 |
| L1 Query 理解 | 解析器（自然语言 → WHERE 条件） | ❌ 发生在检索**之前**，还没有任何文档 |
| L4 LLM 重排 | 打分器（query-doc 相关性 → 整数） | ❌ 输出是分数，不是生成的内容 |

判据很简单：**G 的定义是「消费检索结果、产出自然语言」**。
L0 和 L1 都在检索之前，L4 虽然在检索之后但产出的是排序信号。三个都不沾边。

---

## 那它和 RAG 是什么关系

```
   RAG  =  ┌──────────────┐  +  ┌──────────────┐
           │  Retrieval   │     │  Generation  │
           │              │     │              │
           │  ← 本项目 →   │     │   本项目没有   │
           └──────────────┘     └──────────────┘
```

**这套 L0~L6 基本就是一个 RAG 系统的检索半边该有的样子。**
而且说句不客气的：

> 大多数 RAG 实现的 R，做得比这个项目差得多。

典型的 RAG 是「文档切块 → embedding → 存向量库 → top-k 余弦 → 塞进 prompt」。
对照 [ARCHITECTURE.md](ARCHITECTURE.md) 里批评过的那些点，它几乎全中：
没有 query 理解、没有词汇检索、没有融合、没有重排、没有评估闭环。
**唯一的检索手段就是那条被证明最弱的纯向量路。**

所以那篇文章的价值反而对 RAG 更大——它讲的每一层，RAG 都缺。

---

## 迁到 RAG 要改什么

| 层 | 电商搜索 | RAG | 变化 |
|---|---|---|---|
| L0 | 商品属性抽取 | chunk 元数据抽取（来源、时间、章节、实体） | 同构，换个 schema |
| L1 | query → WHERE 条件 | query 改写 / 分解 / HyDE / 时间范围解析 | 同构，更重要 |
| L2 | BM25 + 向量 + 结构化 | 完全一样 | **原样搬** |
| L3 | RRF | 完全一样 | **原样搬** |
| L4 | cross-encoder 重排 | 完全一样，但更关键 | **原样搬** |
| L5 | 业务排序 + 打散 | **没有对应物** | ⚠️ 删掉 |
| — | — | **去重 + 上下文装配** | ⚠️ 新增 |
| — | — | **生成 + 引用标注** | ⚠️ 新增 |
| L6 | NDCG / CTR / 转化 | NDCG + faithfulness / 引用准确率 | 扩展 |

三个真正的差异值得展开：

### ① 消费者不同，Top-K 的取法就不同

人眼扫商品是「宁滥勿缺」——20 条里有 3 条不相关，用户自己会跳过。

LLM 上下文是「宁缺勿滥」——塞进去一段不相关的内容，
它会真的拿去推理，产出一个自信的错误答案。

所以 RAG 的 K 通常是 5~10，而且 **precision 比 recall 重要**，
这和电商搜索的直觉正好相反。
这也是为什么 L4 重排在 RAG 里比在电商里还关键。

### ② L5 整层消失

广告出价、利润率、新品扶持——这些在 RAG 里没有对应概念，
硬塞进去就是往答案里注入偏见。

多样性打散也变成了另一件事：
电商是「同店最多 2 个」，RAG 是「去掉语义重复的 chunk，别浪费上下文」。

### ③ 评估维度翻倍

检索侧还是 NDCG / Recall，但生成侧要另外量：
答案有没有忠于检索到的内容（faithfulness）、引用标对没有、有没有在检索不到时硬编。

**检索指标好、生成指标差，是 RAG 最常见的失败形态。**

---

## 反过来说

如果在这个项目上加一个「导购助手」——把 Top-20 交给 Claude，让它写一段
「这三双都适合你，A 更轻但支撑弱一点，B 贵 80 块但鞋楦更宽」——
**那一刻它就变成 RAG 了。**

而那个助手的回答质量，几乎完全由前面这六层决定。
检索给它的是错的（比如那双 1680 元的鞋、或者那个矫形鞋垫），
它只会把错误答案说得更有说服力。
