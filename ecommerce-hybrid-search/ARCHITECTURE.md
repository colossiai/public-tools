# 电商搜索的真正难点不在检索，在 query 理解

—— 从一个「一个 SQL 干掉三个微服务」的错误示范讲起

---

## 0. 起点：一个看起来很有说服力的方案

先看一段流传很广的写法。场景是用户搜索「适合扁平足的轻量跑步鞋，500 元以内」，
主张是用 PostgreSQL + pgvector 一条 SQL 替代 Pinecone + Elasticsearch + PostgreSQL 三件套：

```sql
WITH semantic AS (
    SELECT id, product_name, price, image_url,
           1 - (embedding <=> query_embedding::vector(1536)) AS semantic_score
    FROM products
    WHERE price <= 500 AND stock > 0 AND category = '运动鞋'
    ORDER BY embedding <=> query_embedding::vector(1536)
    LIMIT 200
)
SELECT id, product_name, price, image_url,
       ts_rank(to_tsvector('chinese', description),
               plainto_tsquery('chinese', '扁平足 跑步鞋 轻量')) AS keyword_score,
       semantic_score,
       (0.4 * semantic_score + 0.6 * keyword_score) AS final_score
FROM semantic
WHERE to_tsvector('chinese', description) @@ plainto_tsquery('chinese', '扁平足 跑步鞋 轻量')
ORDER BY final_score DESC
LIMIT 20;
```

配套的说法是：结构化预过滤先缩小候选集、向量搜索毫秒级、BM25 算关键词相关性、
混合排序 0.4 给语义 0.6 给关键词。

**这段 SQL 跑不起来，而且就算跑起来了，效果也和描述的正好相反。**

更重要的是，它把整个问题的方向搞错了。这篇文章分三部分：
先把这段 SQL 错在哪讲清楚，再说明这个 query 的真正难点在哪，
最后给出一套能落地的架构和一份可跑的参考实现。

---

## 1. 先拆这个 query：它到底在问什么

在讨论用什么数据库之前，先看清楚用户说了什么。

```
             「适合扁平足的轻量跑步鞋，500 元以内」
                  │        │      │            │
     ┌────────────┘        │      │            └──────────────┐
     ▼                     ▼      ▼                           ▼
┌─────────┐        ┌───────────┐ ┌──────────┐        ┌────────────────┐
│  扁平足  │        │   轻量    │ │  跑步鞋   │        │   500 元以内    │
├─────────┤        ├───────────┤ ├──────────┤        ├────────────────┤
│领域知识  │        │数值属性的  │ │  类目     │        │  数值硬约束     │
│映射问题  │        │形容词伪装  │ │          │        │                │
├─────────┤        ├───────────┤ ├──────────┤        ├────────────────┤
│向量 ✗   │        │向量 ✗     │ │向量 ~    │        │向量 ✗          │
│BM25 ✗   │        │BM25 ✗     │ │BM25 ✓    │        │BM25 ✗          │
└─────────┘        └───────────┘ └──────────┘        └────────────────┘
                                                   
                  真正需要「语义检索」的部分：几乎没有
```

四个片段里，三个是**结构化约束**，一个是**领域知识问题**。

- 「500 元以内」是数值比较。embedding 不编码数值大小关系，
  把「500 元以内」编码进查询向量，得到的只是噪声。
- 「轻量」看着是形容词，实际是 `weight_grams < 260`。
  不翻译它，向量和 BM25 都只能瞎猜。
- 「跑步鞋」是类目，类目树比任何相似度都准。
- 「适合扁平足」——下一节单独讲，它是整道题的核心。

所以这个 query 里，**真正剩给向量检索的语义部分非常少**。
把它当成「向量 vs BM25 怎么融合」的问题来解，一开始就偏了。

## 2. 「扁平足」为什么向量和 BM25 都搜不到

正确答案是**稳定支撑系跑鞋**。这中间隔着一条领域知识链：

```
   用户说的话                                    商家写的话
 ┌──────────────┐                          ┌──────────────────────┐
 │              │                          │  内侧 TPU 稳定片      │
 │    扁平足     │      ✗ 词不一样           │  双密度中底           │
 │              │  ◄────────────────────►  │  抗过度内旋           │
 │              │      ✗ 向量拉不近         │  加固后跟稳定器       │
 └──────┬───────┘                          └──────────┬───────────┘
        │                                             │
        │  BM25：两边没有任何共同词，命中不了            │
        │  向量：「扁平足」在 embedding 空间里离         │
        │        「鞋垫」「足部护理」更近，离            │
        │        「TPU 稳定片」很远                     │
        │                                             │
        ▼                                             ▼
 ┌────────────────────────────────────────────────────────────────┐
 │  显式领域本体（src/ontology.py）                                 │
 │                                                                │
 │     扁平足 ──► 足弓塌陷 ──► 落地过度内旋 ──► 需要稳定支撑结构      │
 │                                                                │
 └───────────────────────────────┬────────────────────────────────┘
                                 ▼
                    support_type = '稳定支撑'
                    
                    ← 到这一步，问题从「语义检索」
                      退化成了「一次 B-tree 查找」
```

这条链**必须被显式写下来**。通用 embedding 模型不掌握它，
也不该指望它掌握——跑鞋、床垫、显卡、化妆品，每个类目都有自己的这套映射。

这带来两个直接后果，也是本文架构的两个支点：

1. **离线**要把商品文案翻译成结构化属性（`support_type`、`weight_grams` …）
2. **在线**要把用户 query 翻译成同一套结构化约束

两边翻译到同一套词汇表上，检索就成立了。

参考实现里刻意埋了几个陷阱来验证这一点：真正适合扁平足的鞋，
描述里**绝不出现**「扁平足」三个字；而少数**不合适**的商品
（矫形鞋垫、1680 元的稳定鞋、中性缓震鞋的营销文案）反而把「扁平足」写进了标题。

```
$ python3 data/gen_products.py
陷阱自检 —— 描述含「扁平足」的商品在 q1 中的标注分：
  id=316  q1标注=0  扁平足专用矫形鞋垫 足弓支撑垫
  id=317  q1标注=0  足弓支撑运动袜 扁平足适用 两双装
  id=318  q1标注=0  顶级稳定支撑跑鞋 PRO MAX 扁平足跑者之选
  id=319  q1标注=0  软弹厚底缓震跑鞋 扁平足也能穿
  id=320  q1标注=0  护踝 运动护具 足弓支撑
```

**每一个字面命中「扁平足」的商品，都是错误答案。**
纯 BM25 会把它们排在最前面。

## 3. 回头看那段 SQL：五个问题

### 3.1 `to_tsvector('chinese', ...)` 在原生 PG 里不存在

PostgreSQL 没有内置的 `chinese` 文本搜索配置。要中文分词得装 `zhparser` 或 `pg_jieba`，
再 `CREATE TEXT SEARCH CONFIGURATION`。这个前提不交代，读者复制粘贴第一步就报错。

本项目绕开了这个问题：在 Python 侧用 jieba 预分词，入库时存成空格分隔的文本，
再用 PG 内置的 `simple` 配置建 tsvector。不需要编译任何扩展。

### 3.2 `ts_rank` 不是 BM25

原文反复说「BM25 全文检索」，但 `ts_rank` / `ts_rank_cd` 只是基于词频和位置的打分，
**没有 IDF，没有文档长度归一化**。

这个区别在本题上很致命：「扁平足」是低频词，「跑步鞋」是高频词。
BM25 会因为 IDF 给「扁平足」很高的权重，`ts_rank` 不会。

要在 PG 里拿到真 BM25，需要 ParadeDB 的 `pg_search`（Tantivy 实现）。
本项目的 `docker-compose.yml` 用的就是 ParadeDB 镜像；
如果扩展不可用，`src/l0_ingest.py` 会自动降级到 `ts_rank_cd`，
并在 bench 里把两者的差距量出来。

### 3.3 权重是假的：量纲不统一

```
semantic_score = 1 - cosine_distance    值域 [0,1]，命中时普遍 0.7 ~ 0.9
ts_rank                                 典型值 0.01 ~ 0.1，无上界
```

代入那个公式：

```
0.4 × 0.85  +  0.6 × 0.06
= 0.340     +  0.036
   ~90%          ~10%
```

这不是估算。`src/l3_fusion.py:naive_weighted()` 原样复现了这个写法，
用一组典型分数跑出来是：

```
语义项 0.332 (90%)  vs  关键词项 0.036 (10%)
```

**语义项贡献了九成。** 而原文的说明是「0.6 权重给关键词，
因为在这个场景下精确匹配比语义更重要」——代码做的正好相反。

两个数量级不同的分数直接加权求和，权重表达的根本不是你以为的意思。

### 3.4 最致命的：那是交集，不是融合

```sql
FROM semantic
WHERE to_tsvector(...) @@ plainto_tsquery('chinese', '扁平足 跑步鞋 轻量')
```

这个 `WHERE` 是**硬过滤**。而且 `plainto_tsquery` 对多个词是 **AND 语义**——
商品描述必须**同时**包含「扁平足」「跑步鞋」「轻量」三个词才能留下。

```
       向量召回 200 条
            │
            ▼
   ┌────────────────────┐
   │  WHERE ... @@ ...  │  ← AND 语义的硬过滤
   └────────┬───────────┘
            ▼
   真正适合扁平足的鞋：描述写的是「TPU 稳定片」    → 被砍掉 ✗
   把「扁平足」写进标题的鞋垫：三个词都有         → 留下来 ✓
```

混合检索的全部价值在于**取并集再融合**：一路召回不到的，另一路能补上。
原方案取了交集，等于给每一路都发了一张否决票，把混合检索的价值取反了。

### 3.5 「结构化预过滤加速向量搜索」——说反了

这是全文最大的技术错误，值得单独一节。

---

## 4. HNSW 的过滤陷阱

原文说「结构化预过滤（`price <= 500 AND stock > 0`）先缩小候选集，
避免向量搜索扫描全表」。**pgvector 的 HNSW 不是这么工作的。**

```
        想象中：预过滤                    实际：后过滤
   ┌──────────────────┐            ┌──────────────────┐
   │   全表 100 万条   │            │   全表 100 万条   │
   └────────┬─────────┘            └────────┬─────────┘
            │                                │
     WHERE 先过滤                       HNSW 图先游走
            │                          (ef_search = 40)
            ▼                                ▼
   ┌──────────────────┐            ┌──────────────────┐
   │   2 万条候选      │            │   40 个候选       │
   └────────┬─────────┘            └────────┬─────────┘
            │                                │
      在子集上跑向量                     WHERE 再过滤
            │                                │
            ▼                                ▼
   ┌──────────────────┐            ┌──────────────────┐
   │  Top 200  ✓      │            │  剩下 3 条  ✗     │
   └──────────────────┘            └──────────────────┘
                                     不报错，只是悄悄地少
```

带 `WHERE` 的 kNN 查询，HNSW 先在图里走出 `ef_search` 个候选（默认 40），
**再**把不满足过滤条件的行丢掉。过滤条件越有选择性，剩下的越少。

后果有两种，都很难受：

- 返回的行数远少于 `LIMIT 200`，甚至为 0。**而且不报错**，召回就是静默地掉了。
- 规划器判断走不动，退化成 `Seq Scan` + 精确距离计算，
  「毫秒级」直接变成几百毫秒。

**把这一点写成方案的优化亮点，是把整道题最难的部分说反了。**

三个真正的缓解手段（本项目全都用上了）：

```sql
-- ① 部分索引：把最高频、最有选择性的过滤条件塞进索引本身。
--    索引里就没有不合格的行，后过滤自然不会丢东西。
CREATE INDEX products_embedding_hnsw
    ON products USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64)
    WHERE stock > 0;          -- ← 关键在这一行

-- ② 迭代扫描（pgvector >= 0.8.0）：候选不够时继续往图里走。
--    这个 GUC 就是为了这个场景加的。
SET hnsw.iterative_scan = relaxed_order;
SET hnsw.max_scan_tuples = 20000;

-- ③ 调大 ef_search，用延迟换召回。
SET hnsw.ef_search = 100;
```

`src/db.py:apply_session_tuning()` 会先探测 `hnsw.iterative_scan` 存不存在，
不存在（pgvector < 0.8.0）就打印一条警告——因为在那些版本上，
这个坑是没有解法的，只能靠部分索引和分区绕。

## 5. 六层架构

理清楚问题之后，架构本身反而是自然的。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                              离  线                                      │
│                                                                         │
│  L0  商品属性抽取                                          ROI 最高      │
│      ┌──────────────────────────────────────────────────────────────┐   │
│      │ 「内侧 TPU 稳定片，抑制落地时的过度内旋。单只重约 268g」        │   │
│      │                          │  LLM / 规则                        │   │
│      │                          ▼                                    │   │
│      │   support_type = 稳定支撑    weight_grams = 268                │   │
│      │   pronation_fit = 过度内旋   width = 标准                      │   │
│      └──────────────────────────────────────────────────────────────┘   │
│      + 评论挖掘（「我扁平足穿着很稳」→ 商品级适配信号）                    │
│      + 领域本体维护（扁平足 ↔ 低足弓 ↔ 过度内旋 ↔ 稳定系）                │
└─────────────────────────────────────────────────────────────────────────┘
                                     │
════════════════════════════════════ │ ═══════════════════════════════════
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                              在  线                                      │
│                                                                         │
│  L1  Query 理解                            缓存命中 ~0ms / LLM 50-150ms │
│      「适合扁平足的轻量跑步鞋，500元以内」                                │
│           │                                                             │
│           ├─ 硬过滤   category=跑步鞋, price<=500, stock>0               │
│           ├─ 软属性   support_type=稳定支撑, weight_grams<=260           │
│           ├─ 语义残余 "适合扁平足日常慢跑"                                │
│           └─ 检索词   跑步鞋 跑鞋 支撑 稳定 内旋 足弓 轻量 轻便            │
│                                                                         │
│                    ⚠ 缓存 + 超时降级，绝不做可用性的硬依赖                │
│                                     │                                   │
│  L2  多路召回（并行，硬过滤全部下推）  ▼                     5-30ms        │
│      ┌───────────┐ ┌───────────┐ ┌───────────┐ ┌───────────┐           │
│      │   BM25    │ │   向量     │ │  结构化   │ │  行为召回  │           │
│      │  词汇匹配  │ │  语义残余  │ │  属性过滤  │ │ i2i / u2i │           │
│      │           │ │   HNSW    │ │  B-tree   │ │ (本项目无) │           │
│      └─────┬─────┘ └─────┬─────┘ └─────┬─────┘ └─────┬─────┘           │
│         各取 100      各取 100      各取 100                             │
│            └─────────────┴─────────────┴─────────────┘                  │
│                                     │                                   │
│  L3  RRF 融合（并集）                ▼                        <1ms       │
│              score = Σ  w_i / (60 + rank_i)                             │
│                                     │                                   │
│  L4  Cross-Encoder 重排             ▼                       20-80ms     │
│              对 Top-50 逐个 (query, doc) 联合打分                        │
│                        ★ 质量提升最大的一层                              │
│                                     │                                   │
│  L5  业务排序 + 打散                 ▼                        <1ms       │
│      relevance × pCTR × 履约 × 库存深度 × 广告，同店最多 2 个            │
│                                     │                                   │
│                                     ▼   Top-20                          │
└─────────────────────────────────────────────────────────────────────────┘
                                     │
  L6  评估闭环 ◄─────────────────────┘
      离线 NDCG@10 / Recall@50    在线 CTR / 转化 / 无结果率
```

下面逐层说要点。

### L0 — 离线属性抽取（投入产出比最高的一层）

用 LLM 批量把商品标题、详情、规格表抽成**类型化字段**：

```sql
support_type     text,     -- 缓震 | 稳定支撑 | 竞速 | 越野
weight_grams     integer,  -- 「轻量」这个形容词的真身
width            text,     -- 标准 | 2E | 4E
pronation_fit    text,     -- 中性 | 过度内旋 | 内旋不足
has_carbon_plate boolean,
cushion_level    integer
```

这一步把「适合扁平足」从一个无解的检索问题，变成了 `WHERE support_type = '稳定支撑'`。

三个工程要点：

**① 属性列允许为 NULL，而且一定会有 NULL。** 文案没写克重就是抽不出来。
参考实现里刻意让 28% 的商品不写克重，跑完 ingest 会打印抽取质量：

```
L0 抽取质量（对照 products.json 的 _gold，仅跑鞋）
  support_type 准确率 : xxx/260 = xx.x%
  weight_grams 覆盖率 : xxx/260 = xx.x%
  ↑ 达不到 100% 是正常的，也是有意保留的。
    正因为 L0 会失败，词汇召回和向量召回这两路才必须存在。
```

**如果 L0 是完美的，就不需要混合检索了**——直接 SQL 查属性就行。
混合检索存在的理由，恰恰是 L0 会失败。

**② 要区分营销话术和实际结构。** 一双中性缓震鞋，文案写「扁平足也能穿」，
它的 `support_type` 仍然是「缓震」。这是 LLM 抽取相对正则的核心优势，
prompt 里必须明确写出这条规则（见 `src/l0_ingest.py:EXTRACT_SYSTEM`）。

**③ 别忘了评论。** 「我扁平足穿这双很稳」这类信息藏在评论里，
聚合成商品级信号之后，在真实电商里的增益经常大于换一个 embedding 模型。

生产上这是离线批处理，走 Batch API 成本减半，只在商品新建或文案变更时跑增量。

### L1 — Query 理解（两个工程细节决定它能不能上生产）

```
「适合扁平足的轻量跑步鞋，500元以内」
        │
        ▼   Claude 解析
{
  "category": "跑步鞋",
  "price_max": 500,
  "support_type": "稳定支撑",
  "weight_grams_max": 260,
  "pronation_fit": "过度内旋",
  "residual_semantic": "适合扁平足日常慢跑",
  "keywords": ["跑步鞋", "支撑", "稳定", "内旋", "足弓", "轻量", ...]
}
```

注意 `residual_semantic`：**只有它会被送去做 embedding**。
「500 元以内」不进向量，它进 `WHERE`。

**① 缓存。** 搜索 query 分布是长尾 Zipf，头部 query 的缓存命中率轻松 80%+。
命中缓存时这一层延迟接近 0，LLM 的成本和延迟问题基本消失。
长尾走小模型（Haiku 级）或自己蒸馏一个 0.5B~3B 的解析模型，50~150ms。

**② 降级。** 给这层一个硬延迟预算（本项目默认 1.5s，生产该更短），
超时、限流、网络错误、schema 不匹配——一律立刻走规则解析：

```python
except Exception:
    # 超时、限流、网络错误、schema 不匹配……一律降级。
    # 搜索的可用性不能被 LLM 拖下水。
    return None
```

参考实现里没有 `ANTHROPIC_API_KEY` 也能跑通全流程，走的就是这条规则路径。
这不是为了 demo 方便，这是生产架构本身该有的样子。

### L2 — 多路召回

四路并行，硬过滤全部下推到每一路里面：

```
                   L1 解析结果
                        │
      ┌─────────────────┼─────────────────┬──────────────────┐
      ▼                 ▼                 ▼                  ▼
┌───────────┐    ┌───────────┐    ┌───────────┐     ┌───────────┐
│   BM25    │    │   向量     │    │  结构化   │     │  行为召回  │
│           │    │           │    │           │     │           │
│ keywords  │    │ residual_ │    │support_   │     │  i2i/u2i  │
│ OR 语义   │    │ semantic  │    │type 等    │     │           │
│           │    │           │    │           │     │ (本项目无) │
│ 精确匹配   │    │ 语义泛化   │    │ L0 兜底   │     │ 个性化     │
│ 品牌型号   │    │           │    │           │     │           │
└─────┬─────┘    └─────┬─────┘    └─────┬─────┘     └─────┬─────┘
      │                │                │                 │
   Top 100          Top 100          Top 100           Top 100
      └────────────────┴────────────────┴─────────────────┘
                               │
                          并集（不是交集）
```

两个容易搞错的点：

**关于 OR 而不是 AND。** 词汇召回用 OR 语义，命中一个词就够进候选集，
排名交给 BM25 和后面的融合。原方案用 `plainto_tsquery` 的 AND 语义，召回直接崩掉。

**关于「硬过滤下推能加速向量搜索」——不能。** 见第 4 节，HNSW 是后过滤。
下推的真正目的是让各路看到**同一个候选空间**，融合出来的排名才有意义；
顺带保证 `stock > 0` 这种业务铁律在每一路都成立。

还有一路本项目没实现但真实电商必须有的：**学习稀疏检索（SPLADE 类）**。
它在倒排索引上做语义扩展——能自己学到「扁平足」要激活「支撑」「稳定」，
既有 BM25 的精确性和可解释性，又有语义扩展能力，还能复用现有倒排基础设施。
本项目 `src/ontology.py` 里那张手工同义词表，本质上是它的穷人版；
真上了 SPLADE，那张表就可以退役。

### L3 — RRF 融合

```
score(d) = Σ  w_i / (k + rank_i(d))            k = 60
```

**只看名次，不看分数。** 这是它相对加权和的核心优势：
余弦相似度和 BM25 分数量纲天差地别，加权和必须先归一化，
而归一化又依赖当前 query 的分数分布，换个 query 就要重调。

RRF 天生无量纲，所以权重里写的 0.4 就真的是 0.4。
`k=60` 出自 Cormack 2009 那篇论文，Elasticsearch / OpenSearch 沿用为默认值。

SQL 里的关键是 `FULL OUTER JOIN`：

```sql
FROM semantic s
FULL OUTER JOIN lexical    l USING (id)     -- 并集
FULL OUTER JOIN structured t USING (id)
```

只被一路召回到的商品，其他路 `COALESCE` 补 0，分数低但**仍在候选集里**，
能不能进 Top-20 交给重排决定。这是一票赞成制，不是一票否决制。

### L4 — Cross-Encoder 重排（质量提升最大的一层）

```
   双塔（召回用）                        交叉编码器（重排用）

   query ──►[编码]──► vec_q ─┐          ┌─────────────────────┐
                             ├─cosine   │  [query, doc] 一起进 │──► 分数
   doc   ──►[编码]──► vec_d ─┘          └─────────────────────┘

   两边编码时互相看不见                   两边在每一层都互相注意
   可预计算，快                          必须实时算，慢
   ↓                                    ↓
   适合从 100 万里捞 100 条               适合从 100 条里排出 20 条
```

只有交叉编码器能回答「这双鞋的 TPU 稳定片，是否回应了『适合扁平足』这个诉求」
——因为它同时看到了两边。双塔在结构上做不到这件事。

代价是不能预计算，每个候选一次前向，所以只能放在召回之后、Top-50 这个量级。

一个实现细节：喂给重排模型的文档表示里要**拼上 L0 抽出来的属性**。
让模型直接看到「类型稳定支撑，重量 268 克」，比让它从
「内侧 TPU 稳定片」自己推，要可靠得多。L0 的成果在这里第二次发挥价值。

### L5 — 业务排序（技术文章最常漏掉的一层）

最终顺序 ≠ 相关性顺序：

```
final = f(相关性, pCTR, pCVR, 履约时效, 库存深度, 利润率, 广告出价, 新品扶持)
        + 多样性打散（同款/同店去重）
```

**在真实电商里，这一层对 GMV 的影响远大于 L2 的召回细节。**

一个必须守住的顺序：**业务排序放在重排之后**。
顺序反了，商业因子会污染相关性判断，你会得到一堆「高佣金但不相关」的结果，
短期 GMV 好看，长期把用户赶走。

打散也别省：不打散的话头部很容易被一个店铺的同款不同色霸占，
用户看到的搜索结果页实际上只有两三个选择。

### L6 — 评估闭环

没有这一层，上面五层全是玄学。

- **离线**：人工标注 query-doc 相关性集，看 NDCG@10 / Recall@100
- **在线**：Interleaving 或 A/B，看搜索转化率、加购率
- **最好用的两个健康指标**：**无结果率** 和 **搜后无点击率**

## 6. 端到端时序与延迟预算

```
  t=0ms
   │
   ├─ L1 Query 理解 ─────────────────────────────┐
   │    缓存命中 (~80% 的 query)          ~0ms   │  超过 150ms 预算
   │    缓存未命中，走小模型            50-150ms  │  立刻降级到规则解析
   │                                             │  规则解析 <5ms
   ├─ L2 多路召回（并行，取最慢那一路）─────────── 5-30ms
   │    ├── BM25        5-15ms
   │    ├── 向量 HNSW   5-30ms   ← ef_search 越大越慢
   │    ├── 结构化      1-5ms
   │    └── 行为召回    2-10ms
   │
   ├─ L3 RRF 融合 ────────────────────────────── <1ms   纯内存
   │
   ├─ L4 Cross-Encoder 重排 ──────────────────── 20-80ms
   │    Top-50 × 一次前向。这是延迟大头，
   │    也是质量大头。要压延迟就减少候选数，不是关掉这层。
   │
   ├─ L5 业务排序 + 打散 ─────────────────────── <1ms
   │
   ▼
  合计   缓存命中时  ~30-110ms
        缓存未命中  ~80-260ms
```

延迟预算的分配原则：**L1 有降级、L4 可减量，其余都是硬成本。**
真要压 P99，第一个动的应该是 L4 的候选数（50 → 30），而不是把 L4 整个砍掉。

## 7. 选型：这是最后一步，不是第一步

到这里才轮到讨论用什么数据库。选型是**规模的函数**，不是质量的函数：

| 场景 | 方案 | 理由 |
|---|---|---|
| < 100 万 SKU，团队 < 5 人 | **PostgreSQL 单体**（pgvector + pg_search） | 够用，运维最省，事务一致性白送 |
| 100 万 ~ 1 亿 SKU，有搜索团队 | **Elasticsearch / OpenSearch 单体** | BM25 + dense + sparse + filter + RRF 全内置，一次查询搞定 |
| 排序逻辑复杂 / 超大规模 | **Vespa** | 唯一把检索 + 过滤 + 张量计算 + LTR 排序放在同一节点、同一次查询里完成的引擎 |

三点值得说清楚：

**① 原文的对比对象是稻草人。** 「Pinecone + Elasticsearch + PostgreSQL 三件套」
是刻意选出来的最差方案。现实是 Elasticsearch / OpenSearch 8.x 自己就能一次查询
做完 BM25 + 向量 kNN + 过滤，还内置 RRF。没人会为了向量再挂一个 Pinecone。
诚实的对比是 **PG 单体 vs ES 单体**。

**② PG 单体真正的优势不是「少两次网络往返」。**
是**商品数据和 embedding 在同一个事务里**：不用双写、不用 CDC，
不会出现「向量库说有货、PG 说卖光了」。这个点原文反而没展开，可惜了。

**③ 纯向量库在电商搜索里基本是多余的一层。**
如第 1 节所示，电商 query 中结构化过滤和词汇匹配的权重远高于纯语义，
把向量单独拆成一个系统，是把最简单的部分做成了独立服务。

至于成本，「降低 60%」这种说法要看规模。1536 维 float32 = 6KB/向量，
1000 万商品就是 60GB 向量加上 HNSW 图开销，全部得常驻内存，
一台 128GB 的实例并不便宜。真要谈成本，先谈 `halfvec` 和二值量化 + 重排
——这能把内存打下来 4~32 倍，比换数据库有效得多。

## 8. 实测

参考实现自带 bench，对比六种方案：

```bash
uv run python bench/compare.py
```

```
方案                NDCG@10   vs BM25  Recall@50   p50(ms)   p95(ms)   说明
────────────────────────────────────────────────────────────────────────────
bm25_only            ......    ......    ......    ......    ......   纯 BM25，无 query 理解
vector_only          ......    ......    ......    ......    ......   纯向量，无 query 理解
naive_weighted       ......    ......    ......    ......    ......   原文写法：交集 + 未归一化加权和
rrf                  ......    ......    ......    ......    ......   并集 + RRF，仍无 query 理解
rrf_qu               ......    ......    ......    ......    ......   + L1 query 理解
rrf_qu_rerank        ......    ......    ......    ......    ......   + L4 cross-encoder 重排
```

**这里故意不填数字。** 原文那三个「召回率提升 37%、精确匹配精度提升 52%、
成本降低 60%」正是本文批评的对象——没有数据集、没有语料规模、
没有 embedding 模型、没有硬件配置，一个百分比不说明任何事情。

本项目不想犯同一个错误，所以：**数字由你在自己机器上跑出来。**
bench 跑完会打印一节「局限」，明确说明这是 320 条合成商品、10 个 query
的小规模评测，只能说明**方案之间的相对趋势**，不构成任何行业基准。

值得关注的不是绝对值，是三个相对关系：

1. `naive_weighted` 应该明显低于 `rrf` —— 交集 + 量纲错误的代价
2. `rrf_qu` 应该明显高于 `rrf` —— query 理解的价值
3. `rrf_qu_rerank` 应该是最高的 —— 重排是质量大头

如果你跑出来的结果不符合这三条，那更值得写一篇文章。

## 9. 一句话总结

> **最好的方案不是选哪个数据库，而是：把 query 里所有能结构化的部分都结构化
> （离线 LLM 属性抽取 + 在线 query 理解），只把真正剩下的那点语义交给向量；
> 然后把大部分质量投入放在 rerank 和业务排序上。**

数据库只是执行层。「一个 SQL 干掉三个微服务」回答的是选型问题
——那是这道题里最不重要的一环。
