# 为什么Web app都是账户密码登录后，获取token，然后用token来继续后续的操作

HTTP 协议的“无状态”特性是采用 Token 机制的核心原因。默认情况下，服务器无法分辨两次请求是否来自同一个用户。
如果每次操作都使用账号密码，在安全、性能和架构扩展上都会面临极大挑战。
核心原因对比
| 维度 | 账号密码（每次请求） | Token 令牌机制 |
|---|---|---|
| 安全性 | 凭据需频繁在网络传输，且前端必须持久化保存明文或密文密码，极易被窃取。 | 密码仅在登录时传输一次。Token 具备时效性，且随时可以被服务端吊销。 |
| 性能开销 | 每次操作都需要数据库查询密码并计算高开销的哈希比对（如 bcrypt）。 | Token（如 JWT）可被快速校验，减轻主数据库的计算与查询压力。 |
| 分布式扩展 | 服务端为了记住登录态，需要将 Session 强绑定在特定服务器，阻碍水平扩容。 | 无状态 Token 可以被集群中的任何一台服务器独立校验，方便微服务架构扩展。 |
| 跨域与权限控制 | 传统 Session 依赖 Cookie，容易受到 CSRF 攻击，且跨域支持较差。 | Token 可以灵活附带细粒度的访问权限（Scope），且天然支持跨域和多端（如 Mobile、Web）。 |
标准 Auth 流程
[客户端/前端]                            [服务端/后台]
     |                                        |
     |---- 1. 提交账号密码 (POST /login) ---->| 校验密码并生成 Token
     |<--- 2. 返回 Token 令牌 ----------------|
     |                                        |
     |-- 3. 请求数据 (Header: Bearer Token) ->| 验证 Token 有效性与权限
     |<-- 4. 返回请求结果 --------------------|

 * 凭据交换： 客户端仅在初始化登录时向认证服务器出示一次账号密码。
 * 令牌发放： 认证通过后，服务端颁发带有签名和过期时间的 Auth Token。
 * 无状态鉴权： 客户端在后续请求的 HTTP Header 中带上 Token，服务端只需校验签名有效性即可确认身份并完成响应。
