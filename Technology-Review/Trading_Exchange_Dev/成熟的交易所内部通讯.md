# **成熟的交易所内部通讯**

成熟的交易所（如 Nasdaq、NYSE、CME，以及数字资产领域的 Binance、Coinbase、OKX 等）在**内部通讯**（即撮合引擎、市场数据分发、风险控制、清算结算系统之间的通信）方面使用的技术与格式极高效、低延迟且可扩展，下面从不同层次详细说明：

## 🧩 一、内部通信核心目标

1.  **超低延迟**：微秒级甚至纳秒级响应。

2.  **高吞吐量**：每秒处理数百万条订单或行情消息。

3.  **可靠性**：消息不丢失、不乱序，具备重放与恢复机制。

4.  **可扩展性**：支持集群部署和横向扩容。

5.  **确定性**：在不同分布节点上需保持一致顺序和状态。

## 📡 二、常见通信技术与协议栈

| **层级** | **技术/协议** | **特点与用途** |
|----|----|----|
| **物理层 & 网络层** | 专用低延迟网络、RDMA (Remote Direct Memory Access)、Infiniband、10G/40G/100G Ethernet | 减少内核态切换与网络栈延迟。 |
| **传输层** | UDP Multicast、TCP、SMC-D、RDMA Verbs | 视场景选择，行情多用UDP组播，撮合与风控多用可靠消息协议。 |
| **消息队列/中间件层** | **Aeron**, **LMAX Disruptor**, **Kafka (低延迟定制版)**, **Chronicle Queue**, **ZeroMQ**, **nanomsg** | 提供高性能消息队列或RingBuffer式通信。 |
| **序列化格式** | **SBE (Simple Binary Encoding)**, **FIX Binary/Fast**, **Google Protobuf**, **FlatBuffers**, **Cap’n Proto**, **JSON (仅限外部API)** | 交易核心多使用SBE或FIX Binary，兼具紧凑性和解码速度。 |
| **一致性协议** | Raft, Paxos, 自研日志复制机制 | 保障撮合引擎和备份节点同步一致。 |

## 🧱 三、典型内部架构与数据流

### 1. 撮合与市场数据通道

Client API (FIX / WebSocket / Binary)

↓

Gateway / Ingress Node

↓

Pre-trade Risk Check

↓

Matching Engine (via SBE messages over Aeron/Disruptor)

↓

Market Data Publisher (UDP Multicast or Aeron Channel)

↓

Downstream Systems (Clearing, Risk, Ledger)

> ⚙️ SBE 的优势：定长字段 + 模板化结构 → O(1) 解码。

## 🔐 四、消息可靠性与时序控制

1.  **序列号机制（Sequence ID）**：每个撮合通道严格单调递增。

2.  **ACK 与重传机制**：用于 TCP 或 Aeron Reliable Channel。

3.  **Replay Server**：新加入节点通过重放历史日志快速同步。

4.  **时间同步**：采用 PTP (Precision Time Protocol) 或 GPS 时钟，确保纳秒级时间戳一致性。

## 🧩 五、例子：Aeron + SBE 在实际交易所的典型用法

- **Aeron** 提供快速、可靠的消息通道（微秒级延迟）。

- **SBE** 用于编解码订单与成交数据。

- **Disruptor RingBuffer** 用于内部线程间传递（撮合引擎内部）。

- **UDP Multicast + SBE 公告流** 用于市场数据分发。

示意：

Order Gateway ──(Aeron + SBE)──▶ Matching Engine ──▶ Market Data Broadcaster

## 📊 六、对外通信（外部API接口）

对外通常采用标准化协议：

- **FIX 4.2 / 4.4 / 5.0 SP2**（机构交易）

- **REST / WebSocket (JSON 或 Protobuf)**（零售交易）

- **Binary Gateway (Protobuf / FlatBuffers)**（高频用户）

## ✅ 七、小结

| **功能模块** | **技术方案** | **格式** | **延迟级别** |
|----|----|----|----|
| 撮合内部通信 | Aeron / Disruptor | SBE / FIX Binary | \< 10 µs |
| 行情分发 | UDP Multicast | SBE / FAST | \< 50 µs |
| 外部API | REST / WebSocket / FIX | JSON / ProtoBuf | ms 级 |
| 风控 & 清算 | Kafka (低延迟配置) / Chronicle Queue | Protobuf | 低 ms 级 |

# **具体的撮合引擎内部通信架构示例**

非常好的问题 👍。  
下面我将给出一个**更具体的撮合引擎内部通信架构示例**——涵盖订单流、消息传输格式、线程间通信机制，以及数据一致性控制。  
这个例子基于实际交易所常用的组合：**Aeron + SBE + Disruptor**，以低延迟与确定性为目标。

## 🧩 一、系统组件与通信方向

┌───────────────────┐

│ Client Gateway(s) │ ← 接收API订单 (FIX, WebSocket, Binary)

└────────┬──────────┘

│ (SBE over Aeron)

▼

┌─────────────────┐

│ Ingress Service │ ← 入队、序列化、风控预检查

└────────┬────────┘

│ (RingBuffer)

▼

┌────────────────┐

│ Matching Core │ ← 撮合引擎主体（单线程或顺序执行）

└────────┬────────┘

│

├─▶ Trade Publisher → UDP Multicast (Market Data)

│

└─▶ Ledger Queue → Settlement / Risk System

## 🚀 二、通信机制层次

| **通信方向** | **技术** | **说明** |
|----|----|----|
| Gateway → Ingress | **Aeron Publication / Subscription** | Aeron 的 IPC 模式或 UDP 通道，用于低延迟传输。 |
| Ingress → Matching | **LMAX Disruptor (RingBuffer)** | 在同进程内避免锁和上下文切换。 |
| Matching → Market Data / Ledger | **Aeron IPC / UDP Multicast / Chronicle Queue** | 撮合结果异步广播与落账。 |

## 📦 三、消息结构（SBE 模板示例）

SBE（Simple Binary Encoding）模板文件定义如下（伪示例）：

\<message name="NewOrder" id="101" description="Create a new order"\>

\<field name="orderId" id="1" type="uint64"/\>

\<field name="symbol" id="2" type="string" length="8"/\>

\<field name="side" id="3" type="enum" presence="required"\>

\<validValue name="Buy"\>1\</validValue\>

\<validValue name="Sell"\>2\</validValue\>

\</field\>

\<field name="price" id="4" type="decimal9"/\>

\<field name="quantity" id="5" type="decimal9"/\>

\<field name="timeInForce" id="6" type="uint8"/\>

\</message\>

发送时，编码器生成紧凑的二进制包，例如：

\[Header\]

MsgType: 101

SeqNum: 100203

\[Body\]

orderId=554321

symbol=BTCUSDT

side=Buy

price=64120.50

qty=1.25

TIF=0

## ⚙️ 四、线程间通信逻辑（以单进程模式举例）

**1️⃣ Ingress Service**

// 从 Aeron 订阅新订单

subscription.poll(fragmentHandler, 100);

// 将订单事件写入 RingBuffer

ringBuffer.publishEvent((event, seq, orderMsg) -\> event.copyFrom(orderMsg));

**2️⃣ Matching Engine Thread**

ringBuffer.handleEventsWith(((event, sequence, endOfBatch) -\> {

// 顺序消费事件

Order order = event.getOrder();

match(order); // 撮合逻辑

// 撮合结果放入 publisher 队列

tradePublisher.publish(order, tradeResult);

}));

**3️⃣ Trade Publisher**

// 将成交广播到 Aeron Multicast

aeronPublication.offer(sbeEncoder.encode(tradeResult));

🔁 整个链路中数据传输完全是**单向流动 + 顺序处理**，保障确定性。

## 🧠 五、数据一致性与容错

| **机制** | **描述** |
|----|----|
| **Sequence ID** | 每个订单流单调递增；撮合结果引用原始 SeqNum。 |
| **同步日志 (Write-Ahead Log)** | Disruptor 发布事件时同时写日志至 Chronicle Queue。 |
| **Snapshot + Replay** | 定期保存 OrderBook 快照；重启后从 Snapshot + WAL 重建状态。 |
| **双引擎热备** | 主撮合实时复制操作日志至备用引擎（Aeron IPC）。 |

## ✅ 七、总结

| **层级** | **技术** | **通信模式** | **特点** |
|----|----|----|----|
| 外部 → Ingress | Aeron + SBE | Publish / Subscribe | 低延迟、零拷贝 |
| Ingress → Match | Disruptor | RingBuffer（内存队列） | 无锁、顺序一致 |
| Match → Market / Ledger | Aeron / UDP / Chronicle | 异步分发 | 解耦、可靠 |
| Persistence | Chronicle Queue / WAL | 顺序日志 | 支持恢复和重放 |
