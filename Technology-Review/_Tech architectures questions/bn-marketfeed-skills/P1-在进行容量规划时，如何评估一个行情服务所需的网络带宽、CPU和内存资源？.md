这是一个**真正“上线前必须算清楚”的问题**。容量规划如果拍脑袋，行情系统不是**丢数据**就是**延迟爆炸**。

我用一套**可量化、可复用的评估方法**，一步步算 **带宽 → CPU → 内存**，你拿着这套公式，换参数就能用。

## **一、容量规划的基本原则（先记住）**

> **用峰值，不用平均值  
> 用 P99，不用均值  
> 预留 30%–50% 余量**

行情系统最怕：

- 开盘 / 拉盘 / 插针

- 客户端集体重连

- 网络抖动

## **二、网络带宽评估（先算这个）**

### **1️⃣ 定义变量**

T = tick 速率（条 / 秒）

S = 单条消息大小（字节）

C = 并发客户端数

F = 平均订阅 fan-out

### **2️⃣ 上游接入带宽（交易所 → 服务）**

Bandwidth_ingress = T × S

示例：

- T = 1,000,000 tick/s

- S = 64 bytes

≈ 64 MB/s ≈ 512 Mbps

👉 **这只是进，不是出**

### **3️⃣ 下游推送带宽（服务 → 客户端）**

Bandwidth_egress = T × S × F

示例：

- 每条 tick 平均推给 50 个客户端

64 MB/s × 50 = 3.2 GB/s ≈ 25.6 Gbps

⚠️ **现实结论**：

- 必须：

  - 分级行情

  - 合并 / 降频

  - 不可能原样全推

### **4️⃣ WebSocket / TCP 额外开销**

- WS frame header：2–14 bytes

- TCP/IP：~40 bytes

- TLS（如果有）：+20–50%

**保守乘 1.3–1.5**

## **三、CPU 资源评估（最容易低估）**

### **1️⃣ 拆 CPU 消耗来源**

CPU = 解码 + 计算 + 序列化 + 网络 IO

### **2️⃣ Tick 处理 CPU**

经验值（现代 x86）：

| **操作**      | **CPU 消耗** |
|---------------|--------------|
| 二进制 decode | ~50–100 ns   |
| K 线更新      | ~30–50 ns    |
| fan-out 入队  | ~50 ns       |

**单 tick ≈ 200 ns**

1,000,000 tick/s ≈ 0.2 CPU core

👉 **tick 本身很便宜**

### **3️⃣ 推送序列化（最贵）**

假设：

- 50 fan-out

- 每次序列化 150 ns

1,000,000 × 50 × 150 ns = 7.5 秒 CPU / 秒

≈ **7–8 核**

👉 这就是为什么：

- 要二进制

- 要模板复用

- 要订阅分组

### **4️⃣ 网络 IO CPU**

- syscall

- buffer copy

- epoll wakeup

经验估算：

- **10 Gbps ≈ 1–1.5 核**

### **5️⃣ 汇总 CPU（示例）**

| **模块**  | **核**    |
|-----------|-----------|
| tick 处理 | 1         |
| K 线计算  | 1         |
| 序列化    | 8         |
| 网络 IO   | 4         |
| 预留      | 4         |
| **总计**  | **18 核** |

## **四、内存评估（决定稳定性）**

### **1️⃣ 行情核心内存**

instrument 数 × K线状态 × 周期数

示例：

- 100k instrument

- 10 个周期

- 每个 K ≈ 64 bytes

100,000 × 10 × 64 ≈ 64 MB

### **2️⃣ RingBuffer / 队列**

- tick ring

- fan-out queue

- snapshot buffer

通常：

256 MB – 1 GB

### **3️⃣ WebSocket 连接内存**

每连接：

| **项**        | **大小**  |
|---------------|-----------|
| socket buffer | 64–256 KB |
| send queue    | 32–128 KB |
| session state | ~1 KB     |

示例：

- 20,000 客户端

- 每个 200 KB

≈ 4 GB

👉 WS 是**内存杀手**

### **4️⃣ 总内存建议**

| **模块**        | **内存**    |
|-----------------|-------------|
| 行情核心        | 1 GB        |
| WS 层           | 4–8 GB      |
| 缓存 / snapshot | 2 GB        |
| 预留            | 30%         |
| **总计**        | **8–12 GB** |

## **五、容量规划流程（推荐步骤）**

1.  明确：

    - 最大 tick/s

    - 最大订阅数

    - fan-out 分布

2.  算 **带宽**

3.  算 **序列化 CPU**

4.  算 **连接内存**

5.  ×1.5 做余量

6.  压测验证（必须）

## **六、压测方法（非常关键）**

### **不要做的事**

❌ 用 JMeter 模拟行情  
❌ 用 sleep 生成 tick

### **正确做法**

- 重放真实行情

- burst + 峰值

- 客户端随机慢速

## **七、一句话总结（面试可直接用）**

> **行情系统容量规划的本质是：  
> 带宽决定是否可行，  
> 序列化决定 CPU 上限，  
> 连接数决定内存生死。  
> 永远按峰值算，并预留至少 30% 余量。**
