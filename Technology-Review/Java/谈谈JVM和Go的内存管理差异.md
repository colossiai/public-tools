JVM和Go的内存管理从上层来看,可能会感觉区别不大,都是有栈有堆有GC的, 但内部实现的差异却非常大, 可以对比着看看二者有哪些实现不同的地方, 无论是纯Go用户还是纯JVM用户,都来看看另外一种截然不同的内存管理细节也是很有趣的,还能扩展一下想问题的思路.

本文作者对JVM和Go的内存管理只是浅尝辄止的程度,可能有些不正确的地方,欢迎在评论中指正.

本文并不偏向谁,完全客观地把利弊事实全部摊牌,何况JVM和Go在内存管理方面的利弊基本上是均衡的,因此请各位不要站队,理性评论.

谈论之前,先做个范围限定,JVM和Go都只看流行的较新的x64体系的版本,毕竟不同的版本实现可能在细节上差别很大.

先从Go开始谈吧, 因为Go的内存管理很大程度跟C很像, 源于自家的TCMalloc.

Go的堆利用了现代OS都有的虚拟内存特性,预留了span,bitmap,arena三个内存空间,分别为512M,16G和512G.

放数据的部分就在arena里,也就是说Go最多只支持512G的堆,这个值应该足够应对当前绝大部分PC和服务器的需求,未来会根据硬件发展情况提升各空间的大小.

arena里是按span来划分区域的,最小的span是8K,最大的是80K,内存的粗分配就是以span为单位的. 每个span都是一个按固定大小分配的小内存池,在最小8字节到最大32K的66个档位中选择一个,其中每个细粒度的分配单位叫slot.

可见,这样会带来一些浪费,一是span内分配经常有剩余的slot,二是66个档位不是很精细会导致slot有过多占用,三是固定大小的分配经常会有slot尺寸不能被span空间整除的尾部空间,不过这些在当代PC/服务器上来看无可厚非了.

这样做会带来一些好处,就是从任意指针的值就能直接判定这个指针所指的地址在哪个span的哪个slot,起始地址在哪.

这个好处对Go来说是非常重要的,因为Go有指针类型,可以指向某对象的任何字段,或某数组/slice的任意位置,对GC来说,需要从一个指针迅速找到并mark其所指的对象.

Go的内存管理先简单介绍到这,我们再来看JVM(HotSpot)是怎样做的.

JVM考虑的体量更大,几乎没限定堆大小的上限,JVM主流的G1是把堆内存完全按region的单位来管理的,每个region在1M到32M之间(运行时只固定用其中一种).

每个region相当于一个小内存池,跟Go的span不同的是region不固定每次分配的大小,总是以8字节的对齐来分配.

每次分配都在一个新region中顺序分配,含有垃圾对象的region会在GC阶段做整理,很可能会导致数据移动(多个region整理到另外多个空的region中).

从这里可以看出,JVM的内存浪费只有region的尾部会有无法分配的空间,但却没有Go那样能从任意指针找到所属对象的能力.

因为JVM的对象指针总是指向对象头部,不会指向对象的中间,所以JVM和Go就分别考虑到这样的差异而设计出差别很大的内存管理方案.

再来对比一下对象的结构.

Go的对象完全是其值本身,没有任何附加数据,而JVM的每个对象都有12,16甚至24字节的头部(根据是否数组,是否使用压缩指针而不同,以下默认以压缩指针来计算).

为什么JVM需要对象的头部信息呢,一是给GC,锁做标记,二是hash数据和分代年龄,三是为了从对象指针就可以获取其类型及动态分派的能力,四是数组类型需要有数量信息.

而Go是怎么不用对象头来实现这些的呢? 首先,Go没有对象锁,偏向锁的设计,也没有hashCode和分代GC的需求.

然后,Go的GC还借助了前面提到的bitmap空间,bitmap空间跟arena的空间一一对应,内存占用了arena的1/32的大小(span区域只占了arena的1/1024大小)

其中一半用来标记arena的哪些位置是指针类型,一半用来给GC做标记,这种集中存放对GC的性能有很大的帮助.

那么Go怎么像JVM那样从指针就能获知其类型的呢,仔细想想Go并不需要这个需求,Go的指针类型没有多态能力,类型完全是静态的,编译期就能确定的.

GC的时候从指针就能获得其对象起始位置和大小,是否含有指针也能在bitmap区中找到,所以GC不需要知道很多类型信息就能正确标记和清除.

那Go是怎么实现多态的呢,答案只有一个:interface. interface的结构很简单,就两个指针,一个指向类型,一个指向对象数据的起始位置.

可见,JVM的指针在Go这边对应的是两个完整指针,无论是传输存储都要一次处理16个字节,而JVM通常用的压缩指针只有4个字节.

当然JVM也有对象头的开销,可见二者不同的设计就有不同的优缺点,哪个设计的更好还真难评判.

最后说下数组,Go的对象和数组都是纯值的嵌入,而JVM的对象和数组中只能嵌入基础值类型和对象指针.

JVM的这种设计会比Go多浪费些内存,也增加不少GC压力,全靠更优秀且复杂的GC算法来挽救,类似.NET的值类型不知道何时能加入到JVM中(不过可以先考虑这个麻烦一些的弥补方案: [dwing：用Java实现大量值对象的紧凑存储](https://zhuanlan.zhihu.com/p/58123370)).

Go通常还使用slice结构来引用数组的整体或一部分,slice的结构也比较简单,一个起始指针和两个长度字段.

两个长度字段竟然都设计成8字节大小,也就是整个slice有24个字节,相比JVM的数组的元素数量只用了4字节,Go可真大方.

JVM的数组跟普通对象差不多,只是在12字节的头后面有4字节的长度,然后就是数组内容.

如果要实现Go的slice,需要封装引用数组对象及其起始位置和长度信息,加上对象头一共是24字节,跟Go的slice一样,但JVM的数组要多16字节的对象头.

另外,Go支持获取数组元素的指针,JVM要实现相同的效果就得把数组对象和索引绑在一起,不过这也同时获得了访问其它元素的能力,而Go的指针却不支持向前后移动.

总之,JVM的对象通常不是很大,所以对象头的开销不可小觑,相比之下Go的1/32的bitmap开销就小不少,即使加上各种浪费的情况. Go只需要注意interface结构比较浪费空间.

以上就是主要的内存使用情况差异,最后再来看看GC的差异.

JVM和Go的GC从原理上来看,都是"标记+清除或整理"类的,只是细节上有不少差异.

JVM这些年不断的改进和更新GC算法,源于垃圾对象容易产生的因素,所以对新生代的GC性能需求非常大,所以很早就开始实现了分代GC,并成为标配(虽然最新实验性质的ZGC还未实现分代).

然后最新的几个GC算法,全都开始支持了对象移动以消减长时间运行的内存碎片问题,划分region的设计更是把碎片问题解决得很彻底,并更容易把空闲内存归还给OS.

Go从前面的内存管理上来看,由于内存空间的划分,分代很难实现,除非推翻重新设计内存管理.

另外由于避免runtime更庞大复杂,移动对象恐怕也不太可能实现了,何况span内存池的设计能减轻了不少内存碎片问题(极端情况除外, 详见[dwing：Go的内存管理缺陷?](https://zhuanlan.zhihu.com/p/54236970)).

因此,JVM和Go的GC发展方向就产生了差异,JVM同时兼顾了GC吞吐量和短暂停的需求,可以让用户有所偏重地选择, **<span class="mark">而Go会避免runtime过于复杂而选择需求较多的短暂停方案,至于吞吐量就让用户尽量利用栈,减少堆分配,自行设计对象池等手段来解决了.</span>**

PS: 简单解释一下JVM的压缩指针.

64位的指针在现代的计算机看起来是很浪费的, 实际上多数OS只用到了40多位虚拟地址空间, 如果堆空间不太大,那么就可以用32位指针就能指向所有可能指向的地址.

普通的32位指针只能指向4G空间, 不过JVM的对象都是8字节对齐的起始地址, 所以可以压缩掉指针中固定为0的低3位, 也就是这32位指针可以有35位的寻址能力, 即32G的寻址空间.

如果JVM启动时指定了不超过32G的最大堆大小, 那么就会启用默认的压缩指针, 指针读写时会做简单的计算修正.

这个计算的开销很小, 如果堆足够小, 那么完全可以不做修正, 堆大些会有移位和加减法, 这在现代CPU上开销非常小, 比因节约内存而更高效利用CPU cache要划算.

JVM正是利用了JIT的优势, 根据堆大小动态生成所需的指针修正指令.

压缩指针的设计目前我只在Hotspot JVM上看到过(补: V8虚拟机新版本也支持了这个技术), 当然也可以由用户在任何语言中手动实现专用的内存池, 利用这个思路节约指针的大小而提高性能.
