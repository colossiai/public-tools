# 经典的竞态条件场景


有很多。TOCTOU 只是 **Race Condition（竞态条件）** 中的一类。对于后端开发、并发编程和交易系统，下面这些非常经典。

## 1. Check-Then-Act（检查后执行）

TOCTOU 本质上属于这一类。

```text
if (balance >= 100)   ← Check
    withdraw(100)     ← Act
```

两个线程同时执行：

```text
Thread A: balance = 100 → 检查通过
Thread B: balance = 100 → 检查通过

Thread A: -100
Thread B: -100

最终 balance = -100
```

**解决：** 原子操作、CAS、锁、数据库条件 UPDATE、事务。

---

## 2. Read-Modify-Write（读-改-写）

这是最常见的并发问题之一。

例如：

```java
counter++;
```

实际上可能是：

```text
1. read counter
2. add 1
3. write counter
```

两个线程：

```text
counter = 10

A: read 10
B: read 10

A: write 11
B: write 11

结果：11
预期：12
```

这叫 **Lost Update（丢失更新）**。

典型场景：

* `counter++`
* 库存扣减
* 账户余额
* 订单数量
* 统计计数器

**解决：**

```java
AtomicInteger.incrementAndGet()
```

或者数据库：

```sql
UPDATE product
SET stock = stock - 1
WHERE id = 1 AND stock > 0;
```

---

## 3. Double-Checked Creation（重复创建）

例如：

```java
if (cache.get(key) == null) {
    cache.put(key, create());
}
```

两个线程：

```text
A: cache.get() → null
B: cache.get() → null

A: create object
B: create object

A: put
B: put
```

结果：

* 创建了两个对象
* 重复初始化
* 重复发送请求
* 重复执行任务

典型场景：

```text
Cache Miss
    ↓
两个请求同时 miss
    ↓
同时访问 DB
    ↓
Cache Stampede
```

**解决：**

* Lock
* `computeIfAbsent`
* SingleFlight
* 分布式锁

---

## 4. Check-Then-Insert（检查后插入）

例如：

```sql
SELECT * FROM user WHERE username = 'alice';
```

发现不存在，然后：

```sql
INSERT INTO user(username) VALUES ('alice');
```

两个请求：

```text
A: SELECT → 不存在
B: SELECT → 不存在

A: INSERT → 成功
B: INSERT → 成功
```

如果没有 unique constraint，就产生重复数据。

**正确做法：**

```sql
ALTER TABLE user
ADD UNIQUE KEY uk_username(username);
```

然后：

```sql
INSERT INTO user(username)
VALUES ('alice');
```

让数据库保证原子性。

## 5. ABA Problem

这是 Lock-free / CAS 中非常经典的问题。

假设：

```text
Initial: A
```

Thread A：

```text
读取 value = A
```

Thread B：

```text
A → B
B → A
```

Thread A：

```text
CAS(A → C) 成功
```

但是 Thread A 不知道中间发生过：

```text
A → B → A
```

这就是 **ABA Problem**。

常见于：

* CAS
* Lock-free stack
* Lock-free queue
* AtomicReference

解决方案：

```text
(A, version=1)
      ↓
(A, version=2)
```

使用：

```java
AtomicStampedReference
```

或者给对象增加 version / generation。

## 6. Lost Wakeup（丢失唤醒）

经典线程同步问题。

```text
Thread A:
    check condition → false

Thread B:
    change condition → true
    signal()

Thread A:
    wait()
```

Thread A 最终可能一直睡眠，因为它错过了 signal。

正确方式通常是：

```java
while (!condition) {
    wait();
}
```

而不是：

```java
if (!condition) {
    wait();
}
```

这是为什么 Java 的 `wait()` 通常必须配合 `while`。

---

## 7. Missed Event / Event Race

例如：

```text
Producer:
    update data
    notify()

Consumer:
    subscribe()
```

如果 Consumer 在 Producer `notify()` 之后才开始等待，就可能错过事件。

```text
Producer: Event
              ↓
              notify()
              
Consumer:        subscribe()
                 ↓
                 永远等不到
```

典型场景：

* Condition Variable
* Event Notification
* Pub/Sub
* WebSocket
* 消息队列消费者启动

解决方式通常不是简单依赖 event，而是：

```text
State + Event
```

例如：

```text
先检查当前 state
如果没有满足条件
    再等待 event
```

---

## 8. Producer-Consumer Race

经典的生产者消费者问题。

例如 Ring Buffer：

```text
Producer:
    write buffer[index]
    publish(index)
```

如果发布顺序错误：

```text
publish(index)
write buffer[index]
```

Consumer 可能：

```text
看到 index 已经 ready
↓
读取 buffer
↓
读取到旧数据 / 未初始化数据
```

这其实涉及：

* Memory Ordering
* Memory Barrier
* Visibility
* Happens-Before

在你关注的 **Disruptor / Aeron / lock-free queue** 中非常重要。

---

## 9. Stale Read（读取过期数据）

Thread A：

```text
x = 0
```

Thread B：

```text
x = 1
```

Thread A 继续读取：

```text
x == 0
```

如果没有正确的同步机制，Thread A 不一定立即看到 Thread B 的修改。

在 Java 中涉及：

```text
volatile
synchronized
Lock
Atomic*
```

本质是 **Memory Visibility Race**。

---

## 10. Race Between Cancel and Execute

非常常见于异步任务。

```text
Thread A:
    cancel(job)

Thread B:
    execute(job)
```

可能发生：

```text
A: cancel
B: execute
```

或者：

```text
B: execute
A: cancel
```

最终：

```text
任务到底执行还是不执行？
```

典型场景：

* Job Scheduler
* Timeout
* Future cancellation
* Order cancellation
* RPC timeout

需要定义明确的状态机：

```text
PENDING
   │
   ├──→ EXECUTING
   │
   └──→ CANCELLED
```

并保证状态转换原子化。

---

## 11. Duplicate Message / Double Processing

例如支付系统：

```text
Request
    ↓
服务处理成功
    ↓
Response 丢失
    ↓
Client Retry
    ↓
服务再次处理
```

结果：

```text
扣款 100
扣款 100
```

这不一定是传统内存 Race Condition，但属于分布式系统中的**竞态问题**。

解决：

```text
Idempotency Key
    +
Unique Constraint
    +
状态机
```

例如：

```text
payment_id = 123
idempotency_key = abc
```

保证：

```text
abc → 只允许成功处理一次
```

# 可以把经典竞态条件归纳成这张图

```text
Race Condition
│
├── 1. Check-Then-Act
│      └── TOCTOU
│
├── 2. Read-Modify-Write
│      └── Lost Update
│
├── 3. Duplicate Creation
│      └── Cache Stampede
│
├── 4. Check-Then-Insert
│      └── Duplicate Record
│
├── 5. ABA Problem
│      └── Lock-Free / CAS
│
├── 6. Lost Wakeup
│      └── Condition Variable
│
├── 7. Missed Event
│      └── Notification / PubSub
│
├── 8. Memory Visibility
│      └── Stale Read
│
├── 9. Ordering Race
│      └── Producer / Consumer
│
└── 10. Distributed Race
       ├── Double Payment
       ├── Duplicate Message
       └── Retry Race
```

如果从你比较熟悉的 **Java / C++ / Go + 高性能并发**角度学习，我认为最值得重点掌握的是：

> **TOCTOU → Lost Update → ABA → Lost Wakeup → Memory Visibility → Memory Ordering → Linearizability → Lock-Free Algorithms**

其中 **Memory Ordering + ABA + Linearizability** 是理解 **Disruptor、Aeron、无锁队列、CAS** 的关键。
